stratum

Zero to deployed

One config, one command: an empty DigitalOcean account to a droplet running a web app behind a firewall. This is the shortest end-to-end path through stratum — it provisions the box (do_droplet), resolves the new IP into a state-backed host, and bootstraps it (docker, ufw, a container) in the same apply.

Time: ~5-10 minutes (mostly the box’s first-boot apt + Docker install on a 1-vCPU droplet). Cost: a $6/mo droplet, billed hourly — the last step destroys it.

Prerequisites

  • A DigitalOcean account and an API token with write scope.
  • An SSH key already imported into the DO account (Settings → Security). Note its name — the config references it.
  • ssh on your PATH, with the matching private key loaded (ssh-agent or ~/.ssh/config).

Install stratum

Prebuilt binaries (Linux, macOS, Windows):

# Linux / macOS
curl --proto '=https' --tlsv1.2 -LsSf https://github.com/kbach-dev/stratum-releases/releases/latest/download/stratum-cli-installer.sh | sh

# Windows
powershell -ExecutionPolicy Bypass -c "irm https://github.com/kbach-dev/stratum-releases/releases/latest/download/stratum-cli-installer.ps1 | iex"

The config

Make an empty directory, export your token, and drop one file in it:

mkdir hello-stratum && cd hello-stratum
export DO_API_TOKEN=dop_v1_...        # or put it in ./.env — stratum auto-loads it

stratum.strat (the default config name — bare stratum plan/apply pick it up automatically; use -c NAME.strat for any other name):

secret "do_token" {
  from_env = "DO_API_TOKEN"
}

# 1. The box. Created via the DO API; stratum waits until it is active
#    and sshd answers before anything below runs against it.
resource "do_droplet" "web" {
  token    = secret.do_token.value
  region   = "sgp1"                 # pick one near you: nyc3, fra1, ...
  size     = "s-1vcpu-1gb"
  image    = "ubuntu-24-04-x64"
  ssh_keys = ["my-key"]             # name of the key in YOUR DO account
}

# 2. The host, backed by the droplet's state. No IP to paste — when the
#    droplet lands in state, host.web.addr becomes root@<its-ip>.
host "web" {
  from_resource = "do_droplet.web"
}

# 3. Bootstrap. `apply` runs independent steps in parallel, so the
#    depends_on edges below are load-bearing, not decoration — they
#    serialize the steps that genuinely cannot overlap.

resource "system_package" "ufw" {
  host  = host.web.addr
  state = "present"
}

# Serialized after the ufw install: both steps drive apt, and two apt
# processes on one host fight over the dpkg lock.
resource "ssh_exec" "install-docker" {
  host       = host.web.addr
  command    = "apt-get -y remove docker.io >/dev/null 2>&1 || true; curl -fsSL https://get.docker.com | sh"
  depends_on = ["system_package.ufw"]
}

# Allow ssh BEFORE enabling ufw, or the firewall locks you out.
resource "system_ufw_rule" "allow-ssh" {
  host       = host.web.addr
  port       = "22/tcp"
  rule       = "allow"
  depends_on = ["system_package.ufw"]
}

resource "system_ufw_rule" "allow-http" {
  host       = host.web.addr
  port       = "80/tcp"
  rule       = "allow"
  depends_on = ["system_package.ufw"]
}

resource "system_service" "docker" {
  host       = host.web.addr
  name       = "docker"
  enabled    = true
  state      = "started"
  depends_on = ["ssh_exec.install-docker"]
}

# `system_ufw { enabled = true }` runs `ufw --force enable` — the step that
# actually activates the ruleset (`systemctl start ufw` alone does not).
# stratum REFUSES this at plan time unless a `system_ufw_rule` allowing the
# host's SSH control port (22/tcp here) is also declared, so you can't lock
# yourself out by forgetting the allow-ssh rule.
#
# `ufw --force enable` still flushes connection tracking, which kills any ssh
# session open at that moment — the edges make it run strictly after every
# other step that holds one. The enable itself is guarded by a dead-man's
# switch (an armed `ufw --force disable` timer, default 120s): if the flush
# drops stratum's own session and it can't reconnect in time, access is
# auto-restored rather than left broken.
resource "system_ufw" "firewall" {
  host       = host.web.addr
  enabled    = true
  depends_on = [
    "system_ufw_rule.allow-ssh",
    "system_ufw_rule.allow-http",
    "system_service.docker",
  ]
}

# 4. The app.
resource "docker_container" "hello" {
  host       = host.web.addr
  name       = "hello"
  image      = "traefik/whoami"
  restart    = "unless-stopped"
  ports      = ["80:80"]
  depends_on = ["system_ufw.firewall"]
}

Plan

stratum plan

stratum plan
============
 + do_droplet.web

1 create, 0 update, 0 replace, 0 delete, 0 no-op

deferred (host pending: web <- do_droplet.web): 7 resources — apply provisions the source first, then converges automatically

The droplet doesn’t exist yet, so host "web" is pending: the plan shows one Create (the droplet) and defers everything that targets the host. Nothing is diffed against a box that doesn’t exist.

Apply

stratum apply -y

One invocation, two rounds. Round one creates the droplet, polls the DO API until it is active with a public IPv4, probes :22 until sshd answers, then blocks until first-boot cloud-init finishes — a fresh box runs apt in the background for a while after sshd is up, and bootstrapping into that loses the dpkg lock race:

[digitalocean] CREATE droplet `web` (sgp1 / s-1vcpu-1gb / ubuntu-24-04-x64)
[digitalocean] waiting for sshd on 203.0.113.10:22 (up to 120s)
[digitalocean] waiting for first-boot cloud-init on 203.0.113.10 (up to 180s)
[digitalocean] droplet `web` is up: id=12345678 ip=203.0.113.10

The droplet is now in state, so the pending host resolves and apply automatically runs a second round — the bootstrap chain converges against root@<ip> (plus stratum’s implicit per-host tuning: a swapfile and sshd OOM protection):

[system] PACKAGE ["ufw"] present on root@203.0.113.10
[ssh] EXEC `install-docker` on root@203.0.113.10
[system] UFW allow 22/tcp on root@203.0.113.10
[system] UFW allow 80/tcp on root@203.0.113.10
[system] SERVICE `docker` enabled=true state=started on root@203.0.113.10
[system] UFW enable=true on root@203.0.113.10 (--force enable)
[docker] CONTAINER `hello` on root@203.0.113.10 (create)

Verify:

curl http://<ip>/        # whoami responds with hostname + headers

The IP is in the apply output, and in state: stratum state show do_droplet.web.

Converge, don’t re-run

stratum plan again: everything NoOps. Edit something — add "8080:80" to ports, change the container image, add a system_file — and apply -y changes only that. If a step fails mid-apply (a network blip, an apt hiccup), the succeeded steps are committed to state and the next apply -y resumes from where it stopped. State lives in .stratum/state.json next to your config.

Teardown

stratum destroy -y --allow-destroy

destroy deletes everything in state in reverse dependency order — container, firewall rules, services, and the droplet last, via the DO API. The droplet and its disk are gone. Without -y it previews the delete list; --allow-destroy is the same explicit gate apply uses for plans that delete.

Keep the secret "do_token" block declared until after the destroy: the droplet delete authenticates with the token, and state only stores a redacted marker that resolves back through the config’s secret block.

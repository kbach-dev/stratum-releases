stratum

Introduction

stratum is a tiny declarative IaC tool, written from scratch in Rust. It’s scoped to system bootstrap: install packages, drop config files, manage systemd services, configure the firewall, and run system-tier containers (Traefik, monitoring agents, log shippers). It can also provision the box it then bootstraps — a DigitalOcean droplet via do_droplet. Describe resources in a .strat file, run stratum plan to preview, and stratum apply -y to make it happen. State lives in a JSON file under .stratum/state.json next to your config.

The tool is intentionally small. No plugin system, no remote backend, no cloud SDK. Providers are first-class crates in the workspace; today there are five:

  • system — packages, services, files, secret files, directories, ufw rules.
  • ssh — shells out to system ssh to run commands and write files.
  • docker — drives the remote docker CLI over SSH (networks, containers, image builds).
  • git — clones and pins git working trees on a remote host.
  • digitalocean — provisions the droplet the others bootstrap, via the DO REST API (do_droplet).

What stratum is not

Stratum is not an app-deployment tool. It will not build your application image, manage per-app environments, or rotate deploys. Stratum’s role stops at “the host has docker, traefik, a firewall, and the right config files.” Reach for a per-app deploy tool from there.

What works today

  • .strat config: host, secret, var, provider, resource blocks; nested maps, lists, string/number/bool values; comments (# and //); refs of the form host.<name>.<field>, secret.<name>.value, and ${var.<name>}; ${...} string interpolation for embedding refs inside larger strings. Vars source a string from env, a git checkout’s HEAD, or a literal — useful for SHA-derived image tags that recreate a container when the source commit changes.
  • Cross-resource refs: <kind>.<name>.<attr> in a resource body (bare or inside ${...}) reads the producer’s last-applied state attr — docker_image.api.image_id, do_droplet.web.ip_address. Each ref injects a depends_on edge on the consumer; a producer not in state yet defers the consumer (plan shows a deferred (ref pending: ...) section) and apply converges it in one bounded extra round once the producer lands.
  • JSON state at .stratum/state.json, with create / update / delete actions and a recursive structural diff that ignores state-only provider-computed fields.
  • CLI: plan (with --refresh for live drift detection and --allow-unresolved-secrets for plan-only review), apply (with -y to execute, --allow-destroy to permit deletes, --check-after for an opt-in self-check, and --max-parallel for concurrent apply), destroy (tear down everything in state), status (per-host resource snapshot), state list, state show, state rm, state merge. Both plan and apply take -r/--replace (force a recreate) and -t/--target (restrict to a resource plus its depends_on closure). Global --env-file for loading env vars before resolving secret { from_env } refs, with auto-load of ./.env when no flag is passed.
  • Repeatable -c on plan/apply: multiple .strat files merge into one document and evaluate together. Hosts and secrets declared in one file are visible to refs in another. Duplicates across files are hard errors that name both paths. See Multi-file configs.
  • Namespaces: a top-level namespace "<n>" { configs = [...] } block declares a deployable slice with its own state file. The CLI’s -n NAME global selects a namespace; the manifest’s shared host / secret / provider blocks are visible to every namespace’s configs. Cross-namespace docker_container port and name collisions are caught at plan time. Implicit per-host tuning resources are kept in a shared state file (.stratum/_shared.json) so multiple namespaces sharing a host don’t fight over them. Bundle mode (no -n) is unchanged.
  • system_package, system_service, system_file, system_secret_file, system_env_file, system_dir, system_ufw_rule, system_swap, system_user, caddy_route (apt + systemd + ufw + file/secret-file/env-file + directory-tree + swapfile + user-account + Caddy reverse-proxy management). system_dir also has an empty-dir mode for pre-creating daemon directories without uploading anything. system_secret_file and system_env_file store sha256 only — plaintext never persists in state.
  • ssh_exec (with optional env map for sensitive shell prefixes), ssh_file (run commands, write files).
  • docker_network, docker_container, docker_image. Containers support depends_on (planner topo-sorts), healthcheck (post-apply readiness wait), memory / memory_swap limits, list-form command for argv passthrough, and pull = false for locally-built images. docker_image builds images on the host with DOCKER_BUILDKIT=1 and tracks the resulting image_id.
  • git_repo (new git provider) clones a remote repo to a fixed path on a host and pins it to a branch, tag, or full SHA. State tracks commit_sha; drift triggers fetch + reset.
  • do_droplet (new digitalocean provider) creates a droplet via the DO REST API, polls until it is active with a public IPv4, then waits for sshd on :22 so downstream ssh_exec / system_* steps don’t race cloud-init. The resolved IP lands in state; a host { from_resource = "do_droplet.X" } block picks it up automatically, and resources can read it directly via do_droplet.X.ip_address. Update is rename-only — region / size / image / ssh_keys changes error with destroy-first. See digitalocean.
  • Secrets v0: secret { from_env = ... } or from_file = ..., referenced as secret.<name>.value or ${secret.<name>.value} inside strings. Plaintext flows to providers; state stores a {__secret, __secret_sha256} marker for whole-leaf matches and a <secret:NAME:sha256:HEX> inline marker for substring matches inside interpolated strings; diff/diff_observed are marker-aware so no perpetual drift; plan output renders object markers as <secret:name sha:abc123>. See Secrets.
  • Planner-side validators: docker_container.ports conflict check across the merged config (fails on (host, ip, host_port) collisions, with 0.0.0.0:N / 127.0.0.1:N symmetry); depends_on topo sort with cycle and unknown-ref detection.
  • Post-apply readiness wait: a docker_container with a healthcheck map blocks subsequent steps until docker inspect reports healthy (60s budget). Otherwise a 500ms cosmetic pause.
  • Provider::read on system_* (except system_ufw_rule), ssh_file, both docker_* kinds, git_repo, and do_droplet — surfaces drift between recorded state and live host reality. (do_droplet reads work in apply --check-after but report unreadable on plan --refresh, because the API token in raw state is a redaction marker.)
  • Opt-in post-apply self-check: stratum apply -y --check-after re-reads each resource after applying and reports post-apply drift: clean (or counts of differ/missing/unreadable). Off by default — it costs one ssh round-trip per resource.
  • content_file = "<relative-path>" on system_file and source_dir = "<relative-path>" on system_dir, resolved against the .strat file’s directory.
  • Destruction guard: stratum apply refuses to run a plan with Delete steps unless --allow-destroy is passed. Error names the resources, the loaded configs, and the state file path.

What does not work yet

  • No drift detection for system_ufw_rule, or ssh_exec without a check command — both return Unknown from read, so they show up in unreadable counts (intentional).
  • No DNS provider.
  • No remote state backend — state is a local JSON file (apply/destroy hold an exclusive OS file lock on it for the duration).
  • Cross-host resource refs — a consumer on host A cannot reference a producer’s state on host B (lookup is same-host, then hostless). Mirrors the depends_on scoping rule.
  • The provider "<name>" { ... } block parses but no shipped provider reads one today.

Install

Prebuilt binaries for Linux, macOS, and Windows:

# Linux / macOS
curl --proto '=https' --tlsv1.2 -LsSf https://github.com/kbach-dev/stratum-releases/releases/latest/download/stratum-cli-installer.sh | sh

# Windows
powershell -ExecutionPolicy Bypass -c "irm https://github.com/kbach-dev/stratum-releases/releases/latest/download/stratum-cli-installer.ps1 | iex"

Or build from source with cargo build --release (binary at target/release/stratum).

Quick start

New here? Zero to deployed goes from an empty DigitalOcean account to a droplet running a container in one apply. The local flavor:

cargo build --release

# write a config
cat > stratum.strat <<'EOF'
host "primary" {
  addr = "root@192.0.2.10"
}

resource "system_package" "curl" {
  host = host.primary.addr
  name = "curl"
}
EOF

# see what would happen
./target/release/stratum plan

# preview again with live drift annotation
./target/release/stratum plan --refresh

# apply for real
./target/release/stratum apply -y

State is written to .stratum/state.json. Inspect it with stratum state list and stratum state show.

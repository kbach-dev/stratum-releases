stratum

CLI

Single binary: stratum. All commands operate against one or more config files (default stratum.strat) and a state file (default .stratum/state.json).

stratum <COMMAND>
commandpurpose
planPrint the diff between config and state.

upApply every declared app/namespace, in declaration order.
destroyDelete every resource tracked in state.
installFetch an app’s bricks, scaffold, and pin the lockfile.
updateRe-fetch an installed app at a new ref and re-pin.
statusPrint per-host resource usage and per-container stats.

state mvRename a resource’s address in state (refactor rescue).

Namespace mode (-n and --manifest)

A namespace is a deployable slice declared in a top-level manifest. When -n NAME is set, the CLI:

  1. Locates the manifest. If --manifest PATH is set, that path is used. Otherwise ./stratum.strat is required to exist; if it doesn’t, the command errors out (requires a manifest, but ./stratum.strat does not exist).
  2. Loads the manifest and looks up the named namespace. If it isn’t declared, the error names every known namespace from the manifest.
  3. Resolves -c from the namespace’s configs = [...]. The manifest itself is always the first file in the merged set, so its host / secret / provider blocks are visible to every per-namespace config.
  4. Resolves -s to (in priority order) the explicit -s on the command line, the namespace’s body-level state = "...", or .stratum/<name>.json.
stratum -n infra plan                          # uses ./stratum.strat, configs from `namespace "infra"`
stratum -n app   apply -y                      # state at .stratum/app.json
stratum --manifest deploy/manifest.strat -n web apply -y

-n and -c are mutually exclusive. Passing both errors out — the namespace’s configs = [...] is the config list, and a -c override would silently shadow the manifest’s intent. Drop the -n to operate in bundle mode, or remove the -c to let the namespace pick.

-s is not mutually exclusive with -n. The CLI default is .stratum/state.json; the namespace’s default is .stratum/<name>.json. If you want to point a namespace’s apply at a custom state file (typically during migration from bundle mode), pass -s explicitly and it wins.

Split state

In namespace mode, state writes to two files instead of one:

  • <state_path> (e.g. .stratum/<name>.json) — every user-declared resource.
  • <state_path's directory>/_shared.json — every implicit per-host _stratum_* resource (auto-injected swap, sshd OOM tuning, sshd reload).

The shared file is what lets multiple namespaces target the same host without each one trying to recreate the tuning resources. The first namespace’s apply creates them; subsequent namespaces see them as no-op. See Architecture: split state for the merge rules.

Cross-namespace conflict checks

Before classification, plan and apply in namespace mode re-load every sibling namespace’s configs (with unresolved secrets tolerated) and walk every docker_container they declare. Two collision classes are caught:

  • Host port — two namespaces declare a docker_container binding the same (host, host_port). The check parses H:C and IP:H:C shapes; ranges and bare-port-random forms are skipped.
  • Container name — two namespaces declare a docker_container with the same (host, name). The default for name is the resource’s label.

Both error messages name the offending resource and the sibling that already claims the port or name:

cross-namespace port conflict on host `root@192.0.2.10`:
  - app::docker_container.web  (current) wants 80
  - infra::docker_container.traefik  (sibling) already claims it

The check runs at plan time and is skipped entirely in bundle mode (no -n).

--env-file and .env auto-load

secret { from_env = "X" } reads std::env::var("X") at config-load time. To avoid having to export X=... (and to keep credentials out of shell history), stratum can load env files before resolving secrets.

stratum --env-file .env.prod plan -c bootstrap.strat
stratum --env-file base.env --env-file overrides.env apply -y

Rules:

  • Auto-load. If --env-file is not passed at all, stratum auto-loads ./.env if it exists. Auto-load is silent on miss — no error if there’s no .env.
  • Explicit list. If --env-file is passed one or more times, only those files are loaded. The auto-.env is not consulted. Every listed path must exist and parse, or the command errors before doing any work.
  • Process env wins. A variable already set in the process environment is never overwritten by a file. This is the 12-factor rule — FOO=x stratum apply keeps FOO=x regardless of what .env says.
  • First-set wins among files. When --env-file a --env-file b is passed, a is parsed first; a variable set in a is not overwritten by b. The CLI prints [env] loaded <path> to stderr for every file successfully loaded.

Useful with secret { from_env = ... }:

# .env
PG_PASSWORD=correcthorsebatterystaple
GH_PAT=ghp_...

secret "pg_password" { from_env = "PG_PASSWORD" }
secret "gh_pat"      { from_env = "GH_PAT" }

The .env file is not committed (add it to .gitignore). For team workflows, check in a .env.example with placeholder values instead.

Deferred resources

After the summary, plan prints one section per deferral cause. A resource is deferred — excluded from the plan entirely, not keyed, not diffed — when something it needs can only come from a state entry that doesn’t exist yet:

deferred (host pending: web <- do_droplet.web): 6 resources — apply provisions the source first, then converges automatically

A state-backed host whose source resource isn’t in state.

deferred (ref pending: docker_image.api.image_id — producer not yet in state): 1 resource
  - root@192.0.2.10/docker_container.api  (waiting on docker_image.api)
  apply creates the producer first, then converges automatically

A cross-resource ref whose producer isn’t in state, grouped by ref path with the consumers listed.

deferred (depends on a deferred resource): 1 resource
  - root@192.0.2.10/ssh_exec.post

Transitive deferral: the resource’s depends_on (declared or injected by a ref) targets something deferred above, so it can’t run this round either.

Deferred resources that are already in state are not planned as Deletes — they’re still declared, just not plannable this round. plan never loops; it shows round one plus these sections. apply resolves them — see below.

Secret rendering

A leaf value that is a secret marker (in either prior or desired) prints as <secret:NAME sha:abc123>, where abc123 is the first six hex chars of the SHA-256 of the plaintext. Enough to spot a rotation; not enough to attack offline. See Secrets.

 ~ docker_container.stratum-postgres
      ~ env.POSTGRES_PASSWORD: <secret:pg_password sha:f7c3bc> -> <secret:pg_password sha:9a1e44>

--refresh: live drift detection

When --refresh is set, stratum calls each provider’s read method for every step that has prior state (i.e. not Create), compares the result against what’s recorded, and prints per-resource annotations:

   docker_container.traefik
      ! DRIFT: image: state="traefik:v2.11" observed="traefik:v3.0"
   system_service.docker
      ! DRIFT: resource missing on host (state says exists)

A footer line summarizes:

drift: clean

Or, when there’s drift:

drift: 2 differ, 1 missing, 4 unreadable
  • differ — read returned data that doesn’t match state on at least one field.
  • missing — read returned Absent (the resource is gone on the host but still in state).
  • unreadable — the provider returned Observed::Unknown (no read impl, or read errored). For system_ufw_rule and ssh_exec, this is always the case by design.

Drift detection is one-sided: fields that exist in state but not in the observed data are ignored (providers don’t surface every field). It is also marker-aware — a state-side secret marker is hashed against an observed plaintext, so secret-bearing fields don’t perpetually drift on every refresh. See Architecture: drift detection and Secrets: drift detection.

Create steps are skipped during refresh — there’s no prior state to compare.

apply refuses to run a plan containing any <unresolved-secret:NAME> placeholder — those only appear via plan --allow-unresolved-secrets, and they’re a plan-only construct. Resolve the secret’s source and retry.

Confirmation gate: without -y, apply prints the plan and stops with Apply? Re-run with -y to execute against remote hosts. There is no interactive prompt — re-run with -y to proceed.

When -y is set, you’ll see this banner before the work starts:

!! Applying: side effects WILL execute on remote hosts.

State is written to --state after every successful apply.

The converge round

When round one left anything deferred — a pending state-backed host or a pending cross-resource ref — and the missing piece landed in state during the round (the droplet was provisioned, the image was built with the referenced attr present), apply runs one more round in the same invocation:

— converge: pending host(s)/ref(s) now in state; planning deferred resources —

The loop is bounded to that single extra round by design; chains of boxes provisioning boxes are out of scope. A ref that still doesn’t resolve after the producer had its chance (the provider never wrote the attr, or the producer failed) is surfaced rather than silently skipped:

[apply] warning: `root@192.0.2.10/docker_container.api` is still deferred — `docker_image.api.image_id` did not resolve; producer `docker_image.api` is not in state with that attr

Locking

apply and destroy hold an exclusive lock on the state file for the whole invocation (both apply rounds, in state-backed-host mode). A second invocation against the same state file refuses immediately:

Error: another stratum apply/destroy is already running against this state file

state file: .stratum/state.json
  held by: apply (pid 31337, started 12s ago)

The lock is the OS file lock on <state>.lock, not the file’s existence — a killed process releases it automatically, so there are no stale locks to delete. The .lock file on disk is inert holder metadata. On Windows the OS lock is mandatory, which blocks the conflicting process from reading that metadata; the error degrades to a generic live-holder line there. In namespace mode the shared _shared.json is locked too, so two namespaces sharing a host can’t interleave writes to the implicit _stratum_* resources. plan takes no lock — it only reads.

Post-apply self-check (--check-after)

The post-apply self-check is opt-in: pass --check-after. When set, after a successful apply stratum re-loads the config, rebuilds the plan against the freshly updated state, and runs refresh_plan against the live host. The result is one summary line:

post-apply drift: clean

Or, when something is off:

post-apply drift: 1 differ, 4 unreadable — run 'stratum plan --refresh' to see details

This catches resources that “applied successfully” according to the provider but don’t actually match reality (rare, but possible — e.g. a systemd service that exits zero from restart but immediately crashes). Unreadable counts are expected when your config includes system_ufw_rule or ssh_exec (without a check) resources; both return Unknown from read by design.

The check costs one ssh round-trip per resource — typically the bulk of total apply latency — which is why it’s off by default. Skip it when iterating quickly; turn it on when you want to verify reality matches state. Without --check-after, apply finishes as soon as the side effects complete.

If the plan was a no-op (Nothing to do.), no apply runs and no post-apply check happens.

--allow-destroy: the destruction guard

This flag exists because of a failure shape that’s easy to hit by accident. Apply a config against a state file that holds resources the config doesn’t declare — by forgetting a -c, by pointing -s at the wrong file, by reusing a bundle state for one slice of a larger deployment — and build_plan will emit a Delete step for every resource in state but not in config. Without a guard, apply executes those deletes, and a single mis-typed command tears down the whole host: containers, networks, services, packages, ufw rules, in roughly the order BTreeMap iteration of <kind>.<name> produces.

The fix is two-part. The structural fix depends on how you organize configs: one state file per host with multi-file configs, or one state file per namespace. The tactical fix is the destruction guard: if a plan contains any Delete step, apply refuses to run unless --allow-destroy is set.

refusing to apply: plan would delete 9 resources not in config:
  - system_ufw_rule.allow-ssh
  - system_service.ufw
  - system_service.docker
  - system_package.ufw
  - system_file.traefik-config
  - docker_network.edge
  - docker_container.traefik
  - ...

loaded configs: app.strat
state file: .stratum/host.json

If this is intended, re-run with --allow-destroy. If not, you may be applying against the wrong state file (-s), or have forgotten a -c flag.

The check fires when PlanSummary.delete > 0 — the list is every step with Action::Delete. The error names:

  • the resources slated for deletion,
  • the loaded config files (so a missing -c is visually obvious),
  • the state file path (so a wrong -s is too),
  • three likely causes.

The guard runs before the -y confirmation gate, so you’ll hit the same bail with or without -y.

When to pass --allow-destroy:

  • You really did remove a resource from config and want it gone on the host.
  • You’re tearing down a whole config (commented out resources, intend a full sweep).

When not to pass it: any time the delete list surprises you. Re-check -s and your -c set.

up

Converge the whole box in one command: iterate every app and namespace declared in the root manifest, in declaration order, and run the normal per-namespace apply for each. This is the operator UX an app-based box is built around:

git clone <your-operator-repo> mybox && cd mybox
cp .env.example .env          # fill values (see `stratum env-example`)
stratum up -y

stratum up --plan             # read-only plans for every unit, no applies
stratum up                    # same plans + one confirmation hint, no applies
stratum up -y                 # apply everything, in order
stratum up -y --allow-destroy # pass the destruction guard through to each apply
FlagDescriptionDefault
--planPlan-only: run a read-only plan for every declared unit (no applies, no state writes) and exit. Same output as running up without -y, minus the confirmation hint
--yes, -ySkip confirmation. Required to actually execute side effects — without it, up only prints each unit’s plan
--allow-destroyPermit destructive Delete actions in any unit’s plan (passed through to each apply). Same guard as apply --allow-destroy
--allow-unresolved-secretsPlan-only: substitute <unresolved-secret:NAME> placeholders for missing secret sources instead of failing (same as plan --allow-unresolved-secrets). Rejected with -y — apply refuses placeholder plans
--max-parallel <MAX_PARALLEL>Maximum number of resources to apply concurrently WITHIN each unit (passed through to each apply). Units themselves always run sequentially, in declaration order4

Semantics:

  • Declaration order is the dependency order. There is no cross-namespace dependency graph — up runs units top-to-bottom exactly as written in the manifest. Put producers (shared infra) before consumers.
  • Apps auto-fetch. A declared app pinned in .stratum/apps.lock but missing from the local cache (fresh clone, CI) is fetched at its pinned rev before anything is planned. An app that was never installed errors with the stratum install hint.
  • Input contracts validate up front. Before the first plan or apply, every unit’s input contract is checked against the environment, and every problem across every unit is aggregated into one error (secret names, never values). A shared var missing for several units is listed once, naming each requirer. Plain namespaces without input blocks are unaffected no-ops.
  • Confirmation is once, up front. Without -y, up prints each unit’s read-only plan and stops with a single Re-run \stratum up -y`hint — the same non-interactive gateapplyuses, but confirmed once for the whole run rather than per unit.–planproduces the same read-only output with no hint (explicit plan-only intent; also the mode where–allow-unresolved-secrets` is accepted).
  • Fail fast. The first failing unit stops the run — later units are not attempted (they may depend on the failed one). The summary names each bucket:
up summary: 1 applied · 1 failed · 2 not attempted
  applied: infra
  failed: steward — ssh: connect to host 192.0.2.10 port 22: Connection timed out
  not attempted: vortex, baitong

Units that applied before the failure keep their saved state — re-running stratum up -y after fixing the problem re-plans them as no-ops and resumes from the failed unit.

Each unit runs with the full namespace-mode wiring: split state (.stratum/<name>.json + _shared.json), the per-unit state lock, and the cross-namespace conflict checks. --max-parallel bounds concurrency within each unit; units themselves always run sequentially. up takes no -n (it iterates all units by definition) — use stratum -n NAME apply for a single one.

destroy

Delete every resource tracked in state, in reverse dependency order — without editing the config. The alternative (deleting the resource blocks from config and running apply -y --allow-destroy) expresses a temporary intent by permanently mutating the config file; destroy says it directly.

stratum destroy                          # preview: the full delete list, exit 0
stratum destroy -y --allow-destroy      # execute
FlagDescriptionDefault
--config, -c <CONFIGS> (repeatable)Config file(s). Same shape as plan/apply; used for secret resolution and the provider registry — desired resources are ignored, the delete set comes from statestratum.strat
--state, -s <STATE>Path to the JSON state file.stratum/state.json
--yes, -ySkip confirmation. Required to actually execute side effects
--allow-destroyAcknowledge the destruction. Required in addition to -y: this command’s only job is irreversible (droplets and their disks included), so it keeps the same explicit gate as apply --allow-destroy
--max-parallel <MAX_PARALLEL>Maximum concurrent steps. Deletes are chained sequentially by the executor regardless, so this only matters if a future plan mixes actions4
--skip-unreachableFor a doomed host that’s already unreachable: pre-probe each SSH host and DROP the deletes for any that don’t answer (they die with the host), instead of letting their ssh timeouts block the run and strand the do_droplet delete — which only needs the DO API. The skipped resources are removed from state too

The plan is the existing planner with an empty desired set: every state-resident resource becomes a Delete, ordered reverse-topo over the depends_on edges recorded in state. The executor runs deletes one at a time in that order — a droplet delete never races the ssh deletes of resources living on it.

Why -c is still required: deletes authenticate with values that state holds only as redaction markers. A do_droplet delete needs the real API token, which resolves back through the config’s secret block. Keep secrets declared until after the destroy.

Partial failure: like apply, state is saved on both success and error paths. If a delete fails mid-run, the already-deleted resources are gone from state and the survivors remain — the next destroy resumes with what’s left.

Namespaces: stratum -n NAME destroy tears down one namespace’s own resources. Implicit per-host _stratum_* resources (swap, sshd-OOM tuning) live in the shared _shared.json and are shared with sibling namespaces — so a namespace destroy deletes a shared resource only when no sibling namespace still has resources on that host. Any that are kept are reported (kept N shared per-host resource(s)…). A single-namespace manifest therefore tears down completely, exactly like the old “empty the configs and apply --allow-destroy” workaround, minus the ceremony.

status

Snapshot per-host resource usage. For each unique host declared in the loaded configs, stratum ssh’s the host and prints uptime + free memory + root-disk usage + per-container CPU/RAM/IO from docker stats --no-stream. One section per host.

stratum status
stratum status -c infra.strat -c app.strat -s .stratum/host.json
stratum status --host root@192.0.2.10

The probe is a single composite shell snippet (one ssh round-trip per host) with sentinel headers (===UPTIME===, ===STATS===) to keep parsing simple. docker stats --no-stream is one snapshot, not the streaming default. If docker is absent or there are no running containers, the section prints (no docker stats available) and moves on.

Errors:

  • A host block with no addr is skipped with a [status] skipping host warning.
  • An SSH failure on one host is logged with [status] <addr>: failed: <reason> but does not stop the loop — remaining hosts are still queried.
  • --host filtering with no match is a hard error: no host matched filter `<arg>` .

status is a between-applies diagnostic — not a replacement for a real monitoring stack. The headline use case is spotting RAM/CPU pressure (a container creeping toward its memory limit, a host swap-thrashing) without leaving stratum’s CLI.

graph

Emit the config’s dependency graph to stdout, as a Mermaid flowchart (default), Graphviz DOT, or structured JSON. Read-only and purely config-side: no SSH, no network, no state mutation.

stratum graph                                  # mermaid, default config
stratum graph -c infra.strat -c app.strat      # merged multi-file graph
stratum -n vortex graph                        # namespace mode, like plan
stratum graph --format dot | dot -Tsvg > g.svg # render with graphviz
stratum graph --format json | jq '.edges'      # machine-readable {nodes, edges}
FlagDescriptionDefault
--config, -c <CONFIGS> (repeatable)Config file(s). Repeat -c to merge multiple .strat files, same shape as plan. Default: stratum.stratstratum.strat
--state, -s <STATE>Path to the JSON state file. Read-only here: it resolves from_resource host addrs and cross-resource refs so the graph matches what plan sees. A missing file is fine — fresh configs still graph, with pending hosts/refs shown as declared.stratum/state.json
--format <FORMAT>Output formatmermaid

Hosts are containers: each host renders as a subgraph (mermaid) / cluster (DOT) holding the resources placed on it — which box a resource lives on is shown by containment, not arrow fan-out. Resources are labelled kind.name; template-instantiated resources appear exactly as plan sees them, post-expansion (system_dir.base_workspace). Secrets (hexagons) sit outside the containers, and a declared-but-unreferenced secret stays out of the graph. Hostless resources (do_droplet, …) stay top-level.

Edges come from the same machinery the planner orders steps with — no separate reference scanner to drift out of sync:

  • solid — depends_on ordering, both explicit and the implicit edges injected for cross-resource references (docker_image.app.image_id), plus host { from_resource = "do_droplet.box" } (droplet points at the host container it becomes);
  • dashed — secret usage (which resources a secret’s value flows into).

The state file is read (never written) so from_resource host addrs and cross-resource refs resolve the way plan resolves them. Both are optional: with no state, pending hosts/refs still graph as declared — nothing is deferred or hidden. Missing secret sources never block graphing (the loader’s allow-unresolved-secrets path is always on here; the graph only needs secret names).

Mermaid output pastes straight into a GitHub comment/README ```mermaid fence or the mdbook; DOT pipes through dot -Tsvg. JSON (--format json) is the lossless, machine-readable view the diagram formats are generated from — an object with nodes (each id/label/category, host nodes carrying a members array for the resources placed on them) and edges (from/to/kind, where kind is depends_on or secret) — deterministically ordered so it diffs cleanly, and ready to pipe to jq or feed other tooling.

A bare template "..." file declares no resources until instantiated, so graphing one alone is an error with a hint — add a module block or graph the config that instantiates it.

env-example

Emit a .env.example skeleton for declared input blocks.

stratum -n steward env-example              # one namespace's/app's inputs
stratum env-example                         # aggregate: every declared app/namespace
stratum env-example -o .env.example         # write a file (--force to overwrite)

With -n <name>, each of that namespace’s inputs becomes a # required comment (annotated , secret and/or , file (path)) followed by NAME=, in declaration order. A namespace with no input blocks prints nothing and exits 0.

Without -n, the contract of every app and namespace declared in the root manifest is aggregated (the up companion — one .env for the whole box). Units are walked in declaration order; a shared input declared by several units (SERVER_IP, say) is emitted once, its comment naming every requirer; annotations are the union across declarers (secret/file if any declarer says so). Apps are resolved through the lockfile + cache exactly as up resolves them, so their fetched contracts are included:

# required — steward, vortex
SERVER_IP=
# required, secret — steward
CLAUDE_CODE_OAUTH_TOKEN=
# required, secret — vortex
BOT_TOKEN=
FlagDescriptionDefault
--out, -o <OUT>Write the generated example to this file instead of stdout. Refuses to clobber an existing file unless --force is also passed
--forceOverwrite the --out file if it already exists

The same declarations drive up-front validation: in namespace mode, plan / apply / destroy check the process environment (after --env-file / .env is layered in) against the contract before doing anything, and aggregate every missing var and missing file into one error. up runs the same check for every declared unit at once — one aggregated error across the whole manifest, before the first plan or apply. See Declared inputs for the error shape.

install

Install an app: fetch its config bricks from git into the project-local cache (.stratum/apps/<app>/<rev>/), scaffold the operator directory, and pin the resolved rev in .stratum/apps.lock.

stratum install steward --git https://github.com/kbach-dev/steward --ref v1.4.0
stratum install steward --git https://github.com/kbach-dev/steward   # default branch HEAD
FlagDescriptionDefault
<APP> (required)Local name for the app. Also the namespace -n <app> resolves to, and the cache subdir under .stratum/apps/
--git <URL> (required)Git URL of the app repo to fetch its bricks from
--ref <REF>Tag, branch, or full commit sha to install. Default: the remote’s default-branch HEAD, pinned to a concrete sha (never left floating)

What it does, in order:

  1. Resolve --ref to a concrete rev. A tag/branch is looked up on the remote; a full sha is taken as-is; an omitted --ref resolves the remote’s default-branch HEAD and pins that sha (never a floating ref).
  2. Fetch the repo at rev into .stratum/apps/<app>/<rev>/.
  3. Read the fetched stratum.strat’s namespace config list + input contract.
  4. Scaffold the current directory — idempotently, never clobbering an existing file:
    • stratum.strat with the app "<name>" { git, ref } block,
    • .env.example generated from the input contract,
    • .stratum/apps/ and .env added to .gitignore if absent.
  5. Pin <app> in .stratum/apps.lock.

Then it prints a next-steps footer:

installed app `steward` (v1.4.0 @ 9c1adeadbeef)
  1. fill in inputs:   $EDITOR .env   (see .env.example)
  2. deploy:           stratum -n steward apply

Re-running install is safe: an existing stratum.strat / .env.example is left untouched with a note, the cache is reused if already present, and the lockfile pin is refreshed. See Apps for the block, lockfile, and cache layout.

update

Update an installed app to a new ref: re-fetch the bricks into the cache and re-pin .stratum/apps.lock. Does not apply — run stratum -n <app> apply afterward to roll the box forward via the normal plan diff.

stratum update steward --ref v1.5.0
stratum update steward                 # re-resolve the currently pinned ref
FlagDescriptionDefault
<APP> (required)Name of an already-installed app (must be in .stratum/apps.lock)
--ref <REF>New tag, branch, or full sha. Default: re-resolve the currently pinned ref (a branch moves to its latest tip; a tag stays put)

With no --ref, the currently-pinned ref’s label is re-resolved: a branch moves to its latest tip, a tag stays put (so a tag pin never silently jumps). If the rev is unchanged, update reports already up to date and does nothing. Otherwise it fetches the new rev, re-pins, and prints the delta:

updated app `steward`:
  ref: v1.4.0 -> v1.5.0
  rev: 9c1adeadbeef -> 3f0012ab77aa
  old cache kept: .stratum/apps/steward/9c1adeadbeef

run `stratum -n steward apply` to roll the box forward.

Old cache directories are left in place. The app must already be in the lockfile — update on an uninstalled app errors and points you at install.

ssh

Open an interactive shell on a managed host — or run a one-off command — without reconstructing the ssh invocation by hand. stratum already knows the connection details, so stratum ssh <host> reuses them:

stratum ssh box                     # interactive shell
stratum ssh box -- systemctl status caddy   # run a command and exit
stratum ssh -c infra.strat web      # host declared in a specific config
FlagDescriptionDefault
--config, -c <CONFIGS> (repeatable)Config file declaring the host. Repeat -c for multiple (single value each, so the positional stays unambiguous). Default: stratum.stratstratum.strat
--state, -s <STATE>State file, used to resolve from_resource host addresses.stratum/state.json
<HOST> (required)The host block name to connect to (or a raw user@addr when it matches no declared host)
<COMMAND> (repeatable)Optional command to run instead of an interactive shell. Everything after -- is passed verbatim: stratum ssh box -- systemctl status

<HOST> is a host block name. stratum resolves it exactly as apply does — including a from_resource host, whose address is read from state (so stratum ssh works against a box provisioned by do_droplet without you ever typing its IP). The session reuses the host’s identity_file, port, jump_host, and any pinned host_key — a pinned host is verified with StrictHostKeyChecking=yes, same as automation. If <HOST> matches no declared block it’s treated as a raw user@addr.

Differences from the automation path:

  • No BatchMode — an interactive session may legitimately need to answer a prompt, so this command allows it (automation keeps BatchMode=yes to fail fast instead of hanging).
  • A TTY is allocated (ssh -t) for the shell case; a one-off -- <cmd> runs without one.
  • stratum execs ssh and exits with ssh’s exit code, so stratum ssh box -- <cmd> is scriptable.

This pairs with host-key pinning and (once built) ephemeral deploy keys: when the key stratum connects with lives under ~/.stratum/, stratum ssh is the way a human reuses it without knowing the path.

state rm

state mv

Rename a resource’s address in state without touching any host. A resource’s state address is its post-expansion <kind>.<name> (see State addresses). Refactor a resource into or out of a module and template expansion prefixes its name with <alias>_ — the address changes, so the next plan sees the old address gone and the new one absent and wants to destroy the live resource and create a fresh one. state mv renames the address in place so the same live resource is tracked under its new name and the plan collapses to a no-op.

# You moved `docker_container.web` into `module "app"`, so its address is
# now `docker_container.app_web`. Plan wants delete web + create app_web.
stratum state mv docker_container.web docker_container.app_web        # preview
stratum state mv docker_container.web docker_container.app_web -y     # rename

Both addresses are <kind>.<name> (or <host>/<kind>.<name> to disambiguate a name that exists on more than one host). The kind must be identical on both sides — mv is a rename, not a retype — and it stays on the same host. depends_on edges elsewhere in state that pointed at the old address are rewritten to the new one in the same operation.

FlagDescriptionDefault
<FROM> (required)Current address, <kind>.<name> or <host>/<kind>.<name>
<TO> (required)New address, <kind>.<name> or <host>/<kind>.<name>
--path, -p <PATH>Path to the JSON state file.stratum/state.json
--yes, -yActually rename. Without it, prints what would change and exits (mirrors apply/destroy: side effects need an explicit -y)

Without -y it previews the rename (and how many depends_on references it would rewrite) and reminds you it’s a state-only edit:

Would rename in .stratum/state.json:
  root@192.0.2.10/docker_container.web  ->  root@192.0.2.10/docker_container.app_web
  (1 depends_on reference will be updated)

This edits state only — it does NOT touch any host.
Re-run with -y to rename.

With -y it renames and prints renamed <from> -> <to> in <path> (with a trailing (N depends_on references updated) when any edges moved). Failure modes:

  • FROM isn’t in state → FROM ... not found in state.
  • FROM is a bare <kind>.<name> that exists on several hosts → ambiguous ... disambiguate with <host>/<kind>.<name>.
  • TO already exists → TO ... already exists in <path> — pick an address that isn't taken.
  • The two kinds differ → kind mismatch: ... mv renames within a kind, it can't change kind.

Renaming after the fact is the escape hatch. The planned durable fix is for a template to ship the rename as moved metadata so expansion migrates the address automatically — tracked in #177.

state merge

Merge two or more state files into one. Used to consolidate per-config state files (e.g. .stratum/infra.json, .stratum/app.json) into one state per host.

stratum state merge \
  -o .stratum/host.json \
  .stratum/infra.json \
  .stratum/app.json
FlagDescriptionDefault
--out, -o <OUT> (required)Output state file path. Must not already exist
<INPUTS> (repeatable, required)Source state files (need at least two)

On success:

merged 2 state files into .stratum/host.json (13 resources)

Failure modes:

  • The output path already exists → refusing to overwrite existing state file ....
  • Any <kind>.<name> key appears in more than one input → key ... present in both X and Y — refusing to merge. There is no last-writer-wins. Resolve the collision (rename one resource, or remove it from one state) and retry.

After merge, verify by running stratum plan against the consolidated state with the full -c set — a non-zero diff means something is off and the old per-config files should not be deleted yet.

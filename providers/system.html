stratum

system

Ansible-shape system bootstrap: install packages, manage systemd units, drop files and directories, configure ufw. Operates against a remote host via the system ssh binary (-o BatchMode=yes -o StrictHostKeyChecking=accept-new). Targets Debian/Ubuntu — package management is apt-only.

All apt invocations use DEBIAN_FRONTEND=noninteractive apt-get -y -o Dpkg::Options::=--force-confold -o DPkg::Lock::Timeout=300, so package installs never hang on prompts, keep existing config files on upgrade, and wait up to five minutes for another apt/dpkg process to release the lock instead of failing instantly — without the lock-wait, two apt steps with no depends_on edge between them race under parallel apply, and on a fresh cloud box unattended-upgrades holds the lock for minutes after boot.

The provider takes no configuration block.

Kinds

system_package

An apt-managed package, present or absent.

resource "system_package" "docker" {
  host  = host.primary.addr
  name  = "docker.io"
  state = "present"
}

# Install several packages in one resource.
resource "system_package" "build-tools" {
  host  = host.primary.addr
  names = ["build-essential", "pkg-config", "git"]
  state = "present"
}
attrrequiredtypedefaultdescription
hostyesstring—SSH target in user@host form.
nameno*stringresource labelapt package name. Falls back to the resource label if omitted.
namesno*list of string—A non-empty list of apt package names, installed/removed in one apt call. Mutually exclusive with name.
statenostringpresentpresent or absent.

*Specify either name or names, not both — setting both is a hard error (specify either name or names, not both). When neither is set, name defaults to the resource label. Documenting name explicitly is the convention so the apt package name doesn’t depend on what you called the resource. An empty names list, or a non-string entry, is a hard error at apply time.

On present, the provider runs apt-get update once per (process, host) before the first install, then apt-get install <packages>. On absent, it runs apt-get remove <packages>.

Stored state mirrors the form you wrote: { host, name, state } for the singular form, { host, names, state } for the list form. read runs dpkg-query and returns Present { state: present|absent }. There is no version field in observed state — version drift is not surfaced.

Delete is best-effort apt-get remove (errors swallowed so a missing package doesn’t fail the apply).

system_service

A systemd unit, started/stopped with enabled/disabled independently controlled.

resource "system_service" "docker" {
  host    = host.primary.addr
  name    = "docker"
  enabled = true
  state   = "started"
}
attrrequiredtypedefaultdescription
hostyesstring—SSH target.
nameyes*stringresource labelsystemd unit name. Falls back to the resource label.
enablednoboolfalseIf true, runs systemctl enable <name>.
statenostringstoppedstarted or stopped.
unitnostringnoneInline unit-file text. Written to /etc/systemd/system/<name>.service (via install -D) and systemctl daemon-reload’d before enable/start, so one resource can install, define, and run a service. Change-tracked by sha256.

Order of operations:

  • (enabled=true, state=started) → enable, then restart, then poll is-active for up to 10s.
  • (enabled=true, state=stopped) → enable, then stop.
  • (enabled=false, state=stopped) → stop (best-effort), then disable.
  • (enabled=false, state=started) → disable (best-effort), then restart, then poll is-active for 10s.

restart (not start) is used deliberately: service_apply runs only when the plan is Create or Update — the unit, an EnvironmentFile, or a depends_on changed — so an already-running service must bounce to pick up the new definition. A NoOp plan never calls this path, so unchanged services are not needlessly restarted. If unit is set, the unit file is written and daemon-reload’d first.

If the 10s is-active poll times out, the provider collects systemctl status --no-pager -n 20 (and journalctl -u <svc> --no-pager -n 50 if the status output is sparse) and includes both in the error message.

Stored state: { host, name, enabled, state }, plus unit_sha256 (the sha256 of the inline unit text) when unit is set. read runs systemctl is-enabled + systemctl is-active in one round-trip and returns Present { enabled, state }; when state tracks a unit_sha256, it also sha256s the on-disk unit file so a hand-edited or removed unit surfaces as drift.

Delete runs systemctl disable --now <name> best-effort. If an inline unit was installed (tracked by unit_sha256), the unit file is removed and daemon-reload’d too, so the resource is fully reversible.

Templated file bodies

By default a content_file payload is copied byte-for-byte — a config file that happens to contain literal ${...}-looking text is shipped untouched. Set template = true to render the file body through the same ${...} string interpolation stratum applies to attribute strings, so a value living inside a config file can be a template input, a var, a secret, a host field, or another resource’s output:

resource "system_file" "caddy" {
  host         = host.box.addr
  path         = "/etc/caddy/caddy.json"
  content_file = "files/caddy.json"
  template     = true
}

// files/caddy.json — rendered at config-load time
{ "email": "${var.acme_email}", "host": "${host.box.addr}" }

Rules:

  • Opt-in only. Without template = true the body is verbatim. This is deliberate: it keeps interpolation from mangling files that legitimately use ${...} syntax.
  • Same grammar. ${ref} uses the exact dotted-path grammar as strings (host.x.y, secret.x.value, var.x, kind.name.attr). A bare ${FOO} (shell style) is a load-time error inside an opted-in file — escape it as \${FOO} to emit a literal ${FOO}. \${ is the only escape processed; every other byte (including lone backslashes and newlines) is preserved.
  • Inputs reach file bodies. Inside a template { ... }, ${input.x} in a shipped file is folded from the module’s binding, so a template can parameterize the config files it ships — no sed, no hand-edit. content_file paths resolve relative to the template’s source file.
  • Secrets are allowed here. The honesty guard that blocks secret.x.value in a verbatim content is relaxed for a templated system_file, because system_file keeps content out of state and plan (both store/diff a sha256, never the bytes — see below). The rendered secret is streamed to the host over SSH stdin and never lands on a leakable surface. It still registers in the substring redaction map, so any echo of the value elsewhere is masked.

The template marker is a config-loader directive: it is stripped before the provider runs and never appears in state.

Upload uses install -D -m <mode> -o <owner> -g <group> /dev/stdin <path> with the content streamed via SSH stdin. The -D flag creates intermediate directories.

The provider sha256-hashes the content; on update, if the new sha matches what’s in prior state, the upload is skipped and the resource logs unchanged (sha256 match).

Stored state: { host, path, content, mode, owner, group, sha256 }. Persisting content means a re-plan with the same config is a no-op (no spurious updates from “content field appeared”).

read runs a single-roundtrip probe that prints either MISSING or <mode>|<owner>|<group>|<sha256>. Returns Absent for missing files, Present { host, path, mode, owner, group, sha256 } otherwise. Note that observed state does not include content — drift surfaces as a sha256 mismatch.

Delete runs rm -f -- <path>.

system_secret_file

Like system_file, but the content is treated as a whole-file secret. The plaintext is streamed via SSH stdin (never argv) and never persists in state. State stores sha256 plus the file permissions only — enough to detect drift, not enough to recover the value.

secret "firebase_sa" {
  from_file = "~/.config/app/firebase-sa.json"
}

resource "system_secret_file" "firebase-sa" {
  host    = host.primary.addr
  path    = "/etc/app/firebase-sa.json"
  content = secret.firebase_sa.value
  mode    = "0400"
  owner   = "root"
  group   = "root"
}
attrrequiredtypedefaultdescription
hostyesstring—SSH target.
pathyesstring—Absolute destination path. Parent dirs are created via install -D.
contentyesstring—File contents. Typically secret.<name>.value — see Secrets. Unlike system_file, there is no content_file attribute; whole-file secrets are sourced through a secret { from_file = ... } block.
modenostring0400File mode, passed to install -m. Default is stricter than system_file (0400 vs 0644) — secret files default to owner-only read.
ownernostringrootFile owner, passed to install -o.
groupnostringrootFile group, passed to install -g.

Upload uses install -D -m <mode> -o <owner> -g <group> /dev/stdin <path> with the content streamed via SSH stdin. The provider hashes the content before sending; on update, if the new sha matches the prior state’s sha and all permissions match, the upload is skipped and the resource logs unchanged (sha256 + perms match).

State shape: { host, path, mode, owner, group, sha256 }. The content field is omitted — recovering the plaintext from state is impossible by design. Plan diff is sha-to-sha: the build_plan normalizer (SECRET_CONTENT_TO_SHA) drops content from desired and substitutes sha256: hash(content) before diffing, so plans never echo plaintext into a content: null -> "<plaintext>" change. See Architecture: secret-content normalization.

Apply log: byte length only — never the content, never the sha.

[system] SECRET_FILE `firebase-sa` -> root@192.0.2.10:/etc/app/firebase-sa.json (1842 bytes, mode=0400 root:root)
[system] SECRET_FILE `firebase-sa` -> root@192.0.2.10:/etc/app/firebase-sa.json unchanged (sha256 + perms match)

Drift detection: read runs the same probe shape as system_file (<mode>|<owner>|<group>|<sha256> or MISSING). Returns Present { host, path, mode, owner, group, sha256 } with no content field. Drift surfaces as sha256 / mode / owner / group mismatch.

Delete runs rm -f -- <path> best-effort.

system_env_file

Renders an env map to a KEY=VALUE file on the host — the format consumed by a systemd EnvironmentFile= directive or a docker --env-file. Each map entry becomes one KEY=value line; keys are sorted alphabetically for deterministic output. The secret-grade counterpart of an env map: the values may be secret.<name>.value refs, they are streamed via SSH stdin (never argv), and only the rendered file’s sha256 reaches state.

This is the safe way to land secrets in a config file that a container or service reads by path, instead of duplicating the value into docker_container.env. Pair it with docker_container.env_file: the secret is declared once here, and the container references the path.

secret "pg_password" {
  from_env = "PG_PASSWORD"
}

resource "system_env_file" "db-env" {
  host = host.primary.addr
  path = "/etc/app/db.env"
  mode = "0600"
  env = {
    POSTGRES_PASSWORD = secret.pg_password.value
    POSTGRES_USER     = "postgres"
    POSTGRES_DB       = "app"
  }
}

resource "docker_container" "db" {
  host       = host.primary.addr
  name       = "db"
  image      = "postgres:16-alpine"
  env_file   = "/etc/app/db.env"
  depends_on = ["system_env_file.db-env"]
}

This renders /etc/app/db.env as (keys sorted):

POSTGRES_DB=app
POSTGRES_PASSWORD=<plaintext>
POSTGRES_USER=postgres
attrrequiredtypedefaultdescription
hostyesstring—SSH target.
pathyesstring—Absolute destination path. Parent dirs are created via install -D.
envyesmap—Map of KEY = value. Each entry becomes one KEY=value line; keys sorted alphabetically. Values are typically secret.<name>.value — see Secrets. A non-string value renders as an empty string.
modenostring0600File mode, passed to install -m. Defaults to owner-only read/write (secret-grade).
ownernostringrootFile owner, passed to install -o.
groupnostringrootFile group, passed to install -g.

Upload uses install -D -m <mode> -o <owner> -g <group> /dev/stdin <path> with the rendered content streamed via SSH stdin. The provider hashes the content before sending; on update, if the new sha matches prior state’s sha and all permissions match, the upload is skipped and the resource logs unchanged (sha256 + perms match).

State shape: { host, path, mode, owner, group, sha256 }. The env map is omitted — recovering the values from state is impossible by design. Plan diff is sha-to-sha: the build_plan normalizer replaces the desired env map with the sha of its rendered KEY=VALUE form before diffing, so plans never echo a value into a env.KEY: null -> "<plaintext>" change. See Architecture: secret-content normalization.

Apply log: key count only — never the keys’ values.

[system] ENV_FILE `db-env` -> root@192.0.2.10:/etc/app/db.env (3 keys, mode=0600 root:root)
[system] ENV_FILE `db-env` -> root@192.0.2.10:/etc/app/db.env unchanged (sha256 + perms match)

Drift detection: read runs the same probe shape as system_secret_file (<mode>|<owner>|<group>|<sha256> or MISSING). Returns Present { host, path, mode, owner, group, sha256 } with no env field. Drift surfaces as a sha256 / mode / owner / group mismatch — rotating a secret changes the rendered sha and triggers a re-upload.

Delete runs rm -f -- <path> best-effort.

system_dir

Manages a directory on the remote host. Two modes, selected by whether source_dir is set:

  • Upload mode (source_dir set) — tars + gzips a local tree in memory, streams it over one SSH connection, extracts on the host, applies chown -R + recursive chmod. Used to ship static assets (an mdbook build output, a static-site bundle) to a host where another container will serve them.
  • Empty-dir mode (source_dir omitted) — just mkdir -p + chown + chmod on the host. No upload. Used to pre-create directories a daemon expects but won’t create itself (e.g. /srv/repos, /var/lib/<daemon>).
resource "system_dir" "book" {
  host         = host.primary.addr
  source_dir   = "../book/book"
  path         = "/srv/stratum-book"
  mode         = "0644"
  dir_mode     = "0755"
  owner        = "root"
  group        = "root"
  delete_extra = true
}
attrrequiredtypedefaultdescription
hostyesstring—SSH target.
pathyesstring—Absolute remote destination. Created with mkdir -p.
source_dirnostring—If set, local directory whose contents are tarred + uploaded. Resolved relative to the .strat file’s directory and canonicalized at config-load time. Must exist and be a directory. If omitted, the resource is in empty-dir mode.
modenostring0644Mode applied to every regular file under path (via find -type f -exec chmod). Has no effect in empty-dir mode.
dir_modenostring0755Mode applied to every directory under path (via find -type d -exec chmod). In empty-dir mode, applied once to path itself.
ownernostringrootRecursive owner, applied with chown -R <owner>:<group>. In empty-dir mode, applied once to path.
groupnostringrootRecursive group.
delete_extranoboolfalseIf true, files in prior state’s manifest but absent from the new manifest are rm -f’d on the host after the upload. Keeps the remote tree in sync as local files are removed. No effect in empty-dir mode (the manifest is always empty).
excludenolist of string—Gitignore-style globs pruned from the upload. Entries are applied when building the manifest, so an excluded file never lands in the manifest, the tar, or the drift manifest_sha256. No effect in empty-dir mode.

The provider walks source_dir with walkdir, applies the exclude globs, sha256-hashes every remaining regular file, and stores the result as { relpath -> sha256 } (POSIX / separators even on Windows). The manifest is digested into a single manifest_sha256; on update, if both the manifest digest and every permission attr match prior state, the upload is skipped and the resource logs unchanged (... manifest match).

source_dir is resolved at config-load time: the value the provider sees is the canonicalized absolute path of <dir-of-.strat-file>/<source_dir>. Using system_dir with source_dir via stratum_config::load_str (no base dir) errors with EvalError::SourceDirNoBaseDir. A missing or non-directory path errors with EvalError::SourceDirMissing.

Stored state: { host, source_dir, path, mode, dir_mode, owner, group, delete_extra, exclude, file_count, manifest_sha256, manifest }. The manifest map is persisted in full so delete_extra can diff prior keys against the new manifest.

read runs find . -type f -print0 | sort -z | xargs -0 sha256sum on the remote tree, returns Absent if the directory is missing, otherwise Present { host, path, file_count, manifest_sha256, manifest }. Drift surfaces as a manifest_sha256 mismatch (or, with delete_extra off, extra keys observed on the host that aren’t in state).

File-count cap. If state’s file_count exceeds 200, read returns Observed::Unknown("system_dir read skipped: file_count N > cap 200") instead of doing the remote sha256 sweep. Drift detection on large trees needs a smarter strategy; today they show up as unreadable in --refresh output. Apply itself is not capped — uploads of any size work.

Delete runs rm -rf -- <path> best-effort.

Empty-dir mode (no source_dir)

Omit source_dir to skip the upload entirely. The provider runs only:

mkdir -p <path>; chown <owner>:<group> <path>; chmod <dir_mode> <path>

The stored state’s file_count is 0, the manifest is {}, and manifest_sha256 is the digest of the empty manifest. delete_extra is recorded but has no effect — there are no manifest entries to diff. read returns Absent if the directory is missing on the host, otherwise Present with file_count: 0 (the host’s tree is also expected to be empty as far as stratum is concerned; any files placed there by other processes don’t drift the manifest).

# Pre-create directories the daemon expects.
resource "system_dir" "etc-app" {
  host = host.primary.addr
  path = "/etc/app"
}

resource "system_dir" "srv-repos" {
  host = host.primary.addr
  path = "/srv/repos"
}

Use this in place of an ssh_exec "mkdir -p ..." chain when a daemon needs the directories to exist before it starts: empty-dir mode is idempotent, drift-detectable (the daemon won’t recreate the dir if path is missing on the host), and the owner/group/mode become declarative.

system_ufw_rule

A single ufw allow/deny rule. Idempotent via ufw itself — adding the same rule twice is harmless.

resource "system_ufw_rule" "allow-ssh" {
  host = host.primary.addr
  port = "22/tcp"
  rule = "allow"
}
attrrequiredtypedefaultdescription
hostyesstring—SSH target.
portyesstring—Port specifier, e.g. 22/tcp, 443/tcp, 8080. Passed verbatim to ufw.
ruleyesstring—allow or deny.

Runs ufw <rule> <port> on create/update. Delete runs ufw delete <rule> <port> best-effort.

Stored state: { host, port, rule }. read returns Observed::Unknown("system_ufw_rule read not implemented (ufw status parsing punted)") — ufw rules always show up as unreadable in drift summaries. This is intentional for v1.

Lockout warning: systemctl start ufw does NOT activate the firewall ruleset. The ruleset becomes active only when the firewall is enabled — use the system_ufw kind for that. Enabling the firewall on a host with no allow rule for its SSH control port would lock you out; stratum refuses that at plan time (see below).

system_ufw

The firewall’s enable state — one per host. Replaces the old raw ssh_exec "ufw --force enable" escape hatch with a first-class, lockout-checked kind.

resource "system_ufw" "firewall" {
  host    = host.primary.addr
  enabled = true
}
attrrequiredtypedefaultdescription
hostyesstring—SSH target.
enablednobooltruetrue runs ufw --force enable; false runs ufw --force disable.
deadman_secsnoint120Dead-man’s-switch window guarding the enable (see below). 0 opts out.

Apply runs ufw --force enable (or --force disable); both are idempotent, so an unchanged plan NoOps and a re-apply is harmless. Delete runs ufw --force disable (the safe direction — it can never lock anyone out). read returns Observed::Unknown — like system_ufw_rule, ufw status parsing is punted for v1, so it shows as unreadable in drift summaries.

Stored state: { host, enabled } (plus deadman_secs when declared, so it doesn’t show as drift).

Plan-time lockout guard. Enabling the firewall over the same SSH connection stratum works through has two lockout paths: (1) enabling default-deny with no allow <ssh-port> rule, and (2) deleting the allow-<ssh-port> rule from config while system_ufw stays enabled. Both are refused at plan time by a cross-resource check (in stratum_core::Registry::validate_desired): any host where the desired config enables ufw MUST also declare a system_ufw_rule allowing that host’s SSH control port (from the host block’s port, default 22), and must not deny it. The error names the exact rule to add.

Dead-man’s switch around enable (self-healing). The plan-time guard makes a permanent lockout impossible to express, but ufw --force enable still FLUSHES connection tracking — which can kill the very SSH session stratum is enabling the firewall through (observed live as a “contaminated box” stratum could no longer reach). To make the enable itself survivable, the system_ufw apply wraps it in a targeted dead-man’s switch:

  1. Arm — immediately before enabling, arm a transient systemd timer on the host: systemd-run --collect --on-active=<deadman_secs>s --unit=stratum-deadman ufw --force disable. The revert fires only if not cancelled (i.e. only on failure), so its direction (disable) is always lockout-safe.
  2. Enable — run ufw --force enable. A dropped transport here (ssh exit 255) is the expected symptom of the conntrack flush, not a failure.
  3. Verify — reconnect on a brand-new ssh connection (never the possibly-dead multiplexed master; the probe forces ControlMaster=no/ControlPath=none) and confirm reachability with a trivial true.
  4. Cancel or let-fire — reconnected → stop the timer (the revert never runs) and the step succeeds. Not reconnected within the window → the timer fires ufw --force disable, access is restored, and the step is marked FAILED (checkpointed state records progress; fix the rule and re-apply).

Set deadman_secs = 0 to opt out (bare ufw --force enable, no guard). Honest scope: this guarantees no lockout and lets stratum survive losing its own connection during enable. It does NOT by itself protect a concurrent, unrelated in-flight ssh step from the same flush — for that, keep the depends_on edges that order the enable strictly after every other ssh-heavy step; see the bootstrap tutorial.

system_swap

A declarative swapfile. Reversible — unlike a raw ssh_exec that runs fallocate/mkswap, deleting this resource turns swap off, removes the file, and strips the /etc/fstab line.

resource "system_swap" "main" {
  host = host.primary.addr
  size = "2G"
}
attrrequiredtypedefaultdescription
hostyesstring—SSH target.
sizeyesstring—Swap size token: 2G, 512M, 1024 (bytes). Units are 1024-based, matching fallocate -l. An unparseable value is a hard error.
pathnostring/swapfileSwapfile path on the host.

Apply is idempotent: if the file already exists at the requested byte-size it is just swapon’d; otherwise it is recreated (fallocate, falling back to dd), chmod 600, mkswap, swapon, and an fstab line is added for persistence.

Stored state: { host, path, size }. read checks whether path exists and returns Absent (missing) or Present echoing the recorded size — a size change is driven by the desired-vs-state token diff at plan time, not by reversing bytes back to a token.

Delete runs swapoff + rm -f and removes the fstab line, best-effort.

A declarative user account. Reversible — delete runs userdel -r.

caddy_route

A declarative reverse-proxy route, managed through Caddy’s admin API (default http://localhost:2019) over SSH. One caddy_route is one host-matched route: a reverse_proxy to an upstream, with optional HTTP basic-auth. TLS is automatic — Caddy auto-provisions a certificate for any host in the route matcher, so there is no tls attribute.

resource "caddy_route" "web" {
  host     = host.primary.addr
  domain   = "app.example.com"
  upstream = "web:3000"
}
attrrequiredtypedefaultdescription
hostyesstring—SSH target.
domainyesstring—HTTP host to match for this route.
upstreamyesstring—Dial address for reverse_proxy, e.g. web:3000.
servernostringmainCaddy server name the route is appended to.
adminnostringhttp://localhost:2019Caddy admin endpoint.
route_idnostringresource labelCaddy @id for the route — the addressable key for upsert/delete.
basic_authnomapnone{ user, password_hash }. Both fields required if present — a partial block is a hard error (fail-closed, no unguarded route). password_hash may be a secret.<name>.value ref.

Apply is idempotent and gated on Caddy readiness: it polls the admin endpoint (~30s budget) so a route op on a fresh box doesn’t race a just-started Caddy container, then DELETEs any route with this @id (404 ignored) and POSTs the fresh route — no duplicate accumulation. The basic-auth bcrypt hash is sent on the POST body over stdin (never argv), and state stores only a sha256 signature, never the hash.

Stored state: { host, route_id, server, admin, domain, upstream, basic_auth_user, sig_sha256 }. read GETs the route by @id and returns Absent (missing) or Present with a recomputed sig_sha256, so a hand-edited route surfaces as a signature mismatch.

Delete runs curl -X DELETE <admin>/id/<route_id> (404 is a no-op success).

References & scope

A reference is a dotted path of identifiers used in place of a literal value.

ref ::= ident ( "." ident )+

The first segment is the root. Three built-in roots are supported, plus resource kinds:

rootresolves toshape
hosta field on a declared host block.host.<name>.<field> (3+ parts)
secretthe resolved plaintext of a declared secret block.secret.<name>.value (exactly 3 parts; value is the only allowed field)
varthe resolved string of a declared var block.var.<name> (exactly 2 parts; no field access)
any resource kinda state attr of a declared resource — its last-applied value.<kind>.<name>.<attr...> (3+ parts; resource bodies only). See Resource references.

A root that is neither a built-in nor a declared resource’s kind errors with unknown resource `<kind>.<name>` in reference ... — the message also lists the valid built-in roots, so a typo’d root (vars.x for var.x) is caught here.

Host references

Form: host.<name>.<field> (at least three segments).

host "prod" {
  addr = "root@192.0.2.10"
  port = 22
}

resource "ssh_exec" "uptime" {
  host    = host.prod.addr   # -> "root@192.0.2.10"
  command = "uptime"
}

Resolution walks the host’s evaluated attrs as a JSON map. Each segment after the host name indexes one level deeper, so nested fields work too:

host "prod" {
  ssh = {
    user = "root"
    addr = "1.2.3.4"
  }
}

resource "ssh_exec" "x" {
  host    = host.prod.ssh.addr   # -> "1.2.3.4"
  command = "true"
}

Secret references

Form: secret.<name>.value. Exactly three segments — value is the only allowed field, since secrets are leaves.

secret "pg_password" {
  from_env = "PG_PASSWORD"
}

resource "docker_container" "db" {
  host  = host.primary.addr
  image = "postgres:16"
  env = {
    POSTGRES_PASSWORD = secret.pg_password.value
  }
}

Secret refs are only allowed inside single-leaf string attrs. They are rejected at config-load time inside system_file.content, system_file.content_file, and system_dir.source_dir — see Secrets: the honesty guard for why.

Var references

Form: var.<name>. Exactly two segments — there is no field access, since a var resolves to a single string. Unlike host and secret, a var reference is almost always written inside a ${...} interpolation, because the resolved value is usually glued into a larger string (an image tag, a build command).

var "app_sha" {
  from_git_sha = "../app"
  default      = "dev"
}

resource "docker_container" "app" {
  host  = host.primary.addr
  image = "app:${var.app_sha}"
  pull  = false
}

A bare var.app_sha (outside ${...}) is also valid wherever a string value is expected, but the interpolation form is the common case. See Vars for sources and precedence.

Resource references

Form: <kind>.<name>.<attr> (at least three segments). Any root that is not host / secret / var is treated as a resource kind. Valid only inside resource bodies — including nested blocks and ${...} interpolation. A resource ref in a host, secret, var, provider, or namespace body is rejected.

resource "docker_image" "api" {
  host    = host.primary.addr
  context = "/srv/repos/api"
  tag     = "api:dev"
}

resource "docker_container" "api" {
  host  = host.primary.addr
  image = "api:dev"
  pull  = false
  env = {
    IMAGE_ID = docker_image.api.image_id   # producer's state attr
  }
}

Resolution: from state, at load time

A resource ref reads the target’s attrs from the state file as they were recorded at the last apply — not from the target’s config block. Segments after <kind>.<name> walk the state attrs as a JSON map, one level per segment, so nested attrs work. The resolved value keeps its type: a number attr stays a number when the ref is bare (inside ${...} it is coerced to its string form like any other interpolated scalar). The attr must be a scalar — string, number, or bool.

Lookup order mirrors depends_on: the consumer’s same-host state key (<host>|<kind>.<name>) first, then the hostless key (<kind>.<name>, where hostless kinds like do_droplet live). Cross-host refs are not expressible — a consumer on host A cannot read a producer on host B.

Pending producers: deferral and converge

If the target is declared in the loaded configs but not in state yet (never applied), the consumer is deferred: excluded from the plan, not keyed, not diffed, not executed. plan reports it in its own section:

deferred (ref pending: docker_image.api.image_id — producer not yet in state): 1 resource
  - root@192.0.2.10/docker_container.api  (waiting on docker_image.api)
  apply creates the producer first, then converges automatically

Resources whose depends_on (declared or injected) targets a deferred resource are transitively deferred too, under a deferred (depends on a deferred resource) section. A deferred consumer that is already in state does not plan as a Delete — the phantom Delete is suppressed; the resource is still declared, just not plannable this round.

stratum apply converges automatically: if a pending ref’s producer lands in state during the round with the referenced attr present, apply runs one bounded extra round so the deferred consumers apply in the same invocation (the same round that resolves pending state-backed hosts). If the ref still doesn’t resolve after that round — the provider never wrote the attr, or the producer itself failed — apply warns instead of staying silent:

[apply] warning: `root@192.0.2.10/docker_container.api` is still deferred — `docker_image.api.image_id` did not resolve; producer `docker_image.api` is not in state with that attr

Implicit depends_on

Every resource ref injects a depends_on edge from the consumer to the producer, merged and deduped with any declared depends_on list. The planner therefore orders the producer first, and a producer Update cascades a re-run of the consumer. The edge lands in the consumer’s attrs, so a pre-existing consumer shows a one-time Update when a ref is first added:

 ~ root@192.0.2.10/docker_container.api
      ~ depends_on: null -> ["docker_image.api"]

The edge also flows into state, which improves delete ordering: the consumer is torn down before its producer.

Staleness: last-applied values

A ref resolves to the value recorded in state at the last apply. When the producer updates in the same round, the consumer still evaluated against the old value — but the injected depends_on cascade forces the consumer to re-run, and its recorded attrs settle on the next plan. This is the same trade state-backed hosts make: state is the handoff medium, one plan/apply cycle behind the live world at worst.

Restrictions

  • Not in the host attr. host = do_droplet.web.ssh_host is rejected — the error points at the supported shape: declare a host block with from_resource = "do_droplet.web" and set host = host.<name>.addr. Hosts are resolved before everything else; a state-read there would be circular.
  • Not at secret-valued attrs. State holds redaction markers, not plaintext; a ref at one errors with a hint to declare a secret block and reference secret.<name>.value instead.
  • No self-reference. ssh_exec.x referencing ssh_exec.x.anything is a hard error; a -> b -> a cycles are caught by the existing depends_on topo sort.

Where each root resolves from

The evaluator collects all leaf blocks first — vars, then hosts, then secrets — before it evaluates providers and resources (see Evaluation order). Vars come first because a host addr may reference var.x; hosts, in turn, see only the var scope (not secrets or other hosts). By the time a resource body is read, the host, secret, and var scopes are fully populated, so any reference into them resolves immediately from the declarations in the loaded configs.

Resource references resolve from a different place: the state file, holding what the producer’s provider returned at the last apply. That’s the only place a computed attr (image_id, ip_address) can come from — it doesn’t exist in any declaration. The split is what keeps evaluation single-pass: declaration order never matters (a consumer may appear before its producer in the file), and a producer that hasn’t applied yet doesn’t fail evaluation — it defers the consumer. Ordering between resources is still expressed with depends_on; a resource ref just injects that edge for you.

References inside strings

A reference may also appear inside a string as ${<ref>} — the placeholder is replaced with the resolved scalar value at evaluation time. The same root rules apply (host.*, secret.*, var.*, and <kind>.<name>.<attr> in resource bodies), and the same honesty guard fires for forbidden attrs. See String interpolation for the grammar and edge cases.

env = {
  DATABASE_URL = "postgresql://app:${secret.pg.value}@${host.primary.addr}:5432/app"
}

Bare identifiers as values

A single identifier with no dots is not a valid value. Either quote it as a string or extend it to a ref. The parser will report bare identifier ... not allowed as value (use a string or a reference like ...).

resource "ssh_exec" "x" {
  host    = prod          # error: bare identifier
  host    = "prod"        # ok — string
  host    = host.prod.addr  # ok — reference
}

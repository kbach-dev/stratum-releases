stratum

Apps

An app "<name>" { ... } block declares a deployable slice whose config bricks live in another git repository instead of in the operator’s tree. stratum fetches those bricks into a project-local cache, pins them to a concrete git revision, and then resolves the app exactly like a namespace. The operator’s directory holds only what is genuinely theirs — a one-line manifest, the .env, the deploy state, and the lockfile.

app "steward" {
  git = "https://github.com/kbach-dev/steward"
  ref = "v1.4.0"
}

The three-step operator workflow:

stratum install steward --git https://github.com/kbach-dev/steward --ref v1.4.0
$EDITOR .env                          # inputs scaffolded from the fetched contract
stratum -n steward apply              # deploy
stratum update steward --ref v1.5.0   # bump; a normal apply rolls the box forward

A manifest declaring several apps/namespaces converges in one command with stratum up — units run in declaration order, pinned revs auto-fetch, and stratum env-example (no -n) emits one aggregated .env.example for the whole box.

An app is sugar over a namespace. The fetched repo declares its own namespace "<name>" { configs = [...], input "..." {...} } contract at its root; stratum loads that from the cache and resolves it to the same { configs, state, inputs } a local namespace produces. The one new capability is that the bricks’ configs resolve against the cache root rather than the operator’s manifest directory.

app_block ::= "app" string "{" attr* "}"

Bodies are literal-only — like host / secret / namespace, references (secret.x.value, host.y.addr) are not allowed. A name resolves to either an app or a namespace, never both; declaring both with the same name errors.

The lockfile

install / update write .stratum/apps.lock, which pins each app to an immutable git revision. Commit it — it is what makes a deploy reproducible from the operator repo alone.

[steward]
git = "https://github.com/kbach-dev/steward"
ref = "v1.4.0"          # the label you asked for
rev = "9c1a…"           # the resolved concrete sha — the real pin

rev (not ref) is the reproducibility guarantee: ref is a moving label, rev is the exact commit stratum fetched and will fetch again on another machine. Any key stratum doesn’t recognize inside a table is preserved verbatim on rewrite, so the format is forward-compatible with a future registry source (registry = "…") with no break.

The cache

Fetched bricks land in a project-local cache, gitignored, keyed by revision:

.stratum/
  apps.lock                       # committed — the pins
  steward.json                    # committed — the deploy state
  apps/                           # gitignored — the fetched bricks
    steward/
      9c1a…/                      # one dir per fetched rev
        stratum.strat             # the app's own namespace/input contract
        …bricks…

The cache is deliberately not a global ~/.stratum: a deploy is reproducible from the operator repo alone, with no hidden machine-wide state. install adds .stratum/apps/ and .env to .gitignore for you; the lockfile and state under .stratum/ stay committed.

Old rev directories are left in place after an update (cheap and auditable); a gc is a possible future addition.

install

stratum install <app> --git <url> [--ref <tag|sha>] resolves the ref to a concrete rev, fetches the bricks into the cache, reads the fetched input contract, scaffolds the operator directory, and pins the lockfile. It is idempotent and never clobbers an existing file — a pre-existing stratum.strat / .env.example is left untouched with a note.

If --ref is omitted, the remote’s default-branch HEAD is resolved to a concrete sha and that is pinned — a ref is never left floating.

See the install CLI reference for flags and the scaffold output.

update

stratum update <app> [--ref <tag|sha>] re-resolves the ref (defaulting to the currently-pinned ref’s label — a branch moves to its latest tip, a tag stays put), fetches the new rev into the cache, and re-pins the lockfile. It prints the rev delta but does not apply:

updated app `steward`:
  ref: v1.4.0 -> v1.5.0
  rev: 9c1adeadbeef -> 3f0012ab77aa
  old cache kept: .stratum/apps/steward/9c1adeadbeef

run `stratum -n steward apply` to roll the box forward.

A plain stratum -n steward apply then rolls the box forward via the normal plan diff. update itself changes nothing on the box.

apply / plan (unchanged surface)

stratum -n steward apply and stratum -n steward plan work exactly as they do for a namespace. If the pinned rev isn’t in the cache (a fresh checkout, or CI), stratum auto-fetches it from the lockfile first — so git clone + fill .env + apply is sufficient on a repeat machine, with no separate install.

The input contract validation runs for apps too, sourced from the fetched manifest — a missing env var fails up front, before any host is touched.

Relationship to namespaces and deployd

An app is a namespace whose bricks are fetched-and-pinned rather than hand-listed. Everything the Namespaces page describes — split state, the input contract, up-front validation, cross-namespace conflict checks — applies once the app is resolved.

The app primitive is plan-time, pull-based config distribution. It is a different layer from deployd (an on-box, push-triggered code-refresh runtime): stratum installs and applies the box — deployd itself included — while deployd handles per-push code refresh. Neither absorbs the other.
